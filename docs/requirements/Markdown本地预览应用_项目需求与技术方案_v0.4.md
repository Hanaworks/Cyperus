## 1. 项目背景与定位

### 1.1 问题

本地 Markdown 文件缺乏足够直接、稳定、好用的**独立预览与阅读体验**。现有应用中的 Markdown 编辑能力通常已较成熟，但查看一个 `.md` 文件时，往往仍需要进入编辑器、打开项目/工作区或切换预览模式。

期望的使用方式更接近 PDF 阅读器：**双击文件，即可直接阅读渲染后的内容**。

### 1.2 产品定位

**一款 Preview-first（预览优先）、面向本地文件的 Markdown 桌面应用。**

- **主要价值：** 高质量、快速、低资源占用的 Markdown 预览和阅读。
- **扩展价值：** 适度增加便利功能，减少阅读过程中与其他程序来回切换。
- **非目标：** 以替代 VS Code、Typora、Obsidian 等专业编辑器为方向，或为功能齐全而堆叠编辑功能。
- **长期边界：** 可以逐步增加编辑、转换、导出等能力，但不改变“预览是核心体验”的定位。

### 1.3 产品原则

1. **直接打开：** 不强制导入、创建项目、索引知识库或配置工作区；可选打开文件夹浏览现有文档，不向该目录写入工作区文件。
2. **预览优先：** 默认展示渲染后的 Markdown，而不是源代码。
3. **兼容优先：** 尽可能正确呈现真实 Markdown 文档和常见扩展语法。
4. **性能优先：** 大文件、多文档不能成为卡顿、持续高 CPU 或内存失控的理由。
5. **非侵入：** 默认不修改用户文件；阅读设置不写入 Markdown 正文。
6. **便捷扩展：** 新增辅助功能需要有明确使用价值，并保持良好体验。
7. **渲染器优先选型：** 已暂定 Web 文档排版为开发主线；原 M0 原生对照已按用户决定跳过，不能将主线选择误称为已通过性能验证。
8. **可诊断的运行依赖：** 在未来发布阶段，应能检测、解释并指导修复缺失的 WebView/图形依赖等问题。

## 3. 需求优先级与版本范围

- **P0 — 首版核心：** 缺少则不能达到产品基本目标。
- **P1 — 阅读增强：** 重要但不阻断核心版本发布，可与后续体验版本一起交付。

### 3.2 两套 Theme 的边界

**App Theme（应用主题）**
- 作用范围：标题栏、工具栏、标签页、侧边栏、设置、弹窗、交互组件等。
- 支持独立选择、明暗模式和设置持久化。

**Markdown Theme（文档主题）**
- 作用范围：正文背景、标题层级、字体、段落、引用、表格、任务列表、链接、代码块等。
- Mermaid、代码高亮、数学公式的样式作为**文档主题内部适配**，不升级为第三套同级主题系统。
- 与 App Theme 自由组合，例如“深色应用外壳 + 浅色纸张正文”。
- 文档主题尽量采用独立样式作用域，防止应用样式与文档样式互相污染。

### 3.3 Live Reload（外部修改实时更新）细则

1. 监听已打开文档的文件系统变化；支持常见的**直接覆写**和**临时文件替换/重命名保存**模式。
2. 合并连续/重复事件，避免每次事件都立即执行完整解析。
3. 重新读取前检查文件可用性；发生短暂写入竞争时进行有限重试。
4. 使用文档版本号或任务代次，阻止较旧的渲染结果覆盖较新的内容。
5. 当前活动文档优先刷新；非活动文档可标记为失效并延迟高成本渲染。
6. 尽可能保留当前章节、滚动位置和搜索上下文；不强制跳回顶部。
7. 已不存在的文件提示异常并尽可能保留最后可读内容。
8. 未来如引入内置编辑且存在未保存修改，必须区分外部变更和本地改动，避免静默覆盖用户编辑内容。

### 3.4 预览内链接点击跳转细则（FR-019）

**目标：** 正文中的所有链接都必须可点击，并按链接类型进入正确的目标，不得出现“点了没反应”“跳到空白页”或“在预览里打开脚本地址”这三种失败。

1. **必须可点击的链接类型**：行内链接、引用式链接、自动链接（`<https://…>`）、GFM 自动链接文本、脚注引用与回链、标题锚点、图片包裹的链接、GitHub Alerts 内的链接、表格单元格内的链接、列表/引用内的链接。
2. **按类型分流**（应用必须自行判断，不依赖 WebView 默认导航）：

   | 链接形态 | 行为 |
   |---|---|
   | `#anchor`（页内锚点） | 在当前文档内滚动到目标元素，并给出短暂视觉提示；目标不存在时给出可见提示而非静默失败 |
   | 相对/绝对路径且扩展名为 `.md` `.markdown` `.mdown` `.mkd` | 在应用内以**新标签**打开；若目标已打开则激活已有标签；支持 `目标.md#anchor` 形式并在新标签完成渲染后定位 |
   | 其他本地文件（图片、PDF、压缩包、源代码等） | 交给操作系统默认程序打开；不得在预览区内嵌加载 |
   | `http:` / `https:` / `mailto:` | 交给系统默认浏览器/邮件客户端打开 |
   | `javascript:` `vbscript:` `data:` `file:` 及未知 scheme | **一律拦截**并给出可见提示，不得执行，不得传给系统 |

3. **跳转必须保持应用内导航语义**：外链不得在当前 WebView 内发生顶层导航（否则会离开应用界面且无法返回）。
4. **同一文档内的跳转不得重建标签**：点击锚点不得触发重新解析、不得丢失滚动位置以外的阅读状态。
5. **可访问性与可发现性**：
   - 链接必须可通过 `Tab` 聚焦并可用 `Enter` 激活；聚焦态必须有可见焦点样式。
   - 正文链接与普通文本必须有可区分的视觉样式（颜色 + 下划线或等效手段），且不依赖颜色单一线索。
   - 悬停必须可得知目标（显示目标路径或 URL）。
6. **可中断与可反馈**：目标文件不存在、无权限、正在被占用、路径越界时，必须给出可理解的中文提示并保留当前阅读位置；应用不得崩溃、不得留下空白标签。
7. **修饰键语义**（与常见阅读器一致）：

   | 操作 | 本地 Markdown 链接 | 外部链接 |
   |---|---|---|
   | 普通点击 | 新标签并激活 | 系统浏览器 |
   | `Ctrl` + 点击 | 新标签但**不**激活（后台打开） | 系统浏览器 |
   | 中键点击 | 新标签但不激活 | 系统浏览器 |

8. **不破坏非破坏性约束**：点击链接不得修改任何 Markdown 源文件，不得写入被引用文件。

### 3.5 多标签阅读界面细则（FR-020）

**目标：** 以标签页承载多文档阅读，形态参照 Chrome / VS Code，使“同时读多份文档”成为主路径而不是附加能力。

1. **标签栏位置与形态**：位于窗口顶部、正文之上；标签横向排列、可横向滚动或收纳为溢出下拉；标签数量无硬上限。
2. **单个标签必须呈现的信息**：
   - 文件名（不含目录，超长时中间省略并保留扩展名）
   - 悬停显示完整路径
   - 当前活动标签有明显视觉区分
   - 状态标记：外部已修改未刷新、已失效（文件被删除/不可读）、加载中
   - 关闭按钮（活动标签与其他标签的关闭按钮可常驻或悬停显示，但必须可点击）
3. **必备操作**：

   | 操作 | 触发方式 |
   |---|---|
   | 新建标签（打开文件） | 打开文件、拖入文件、链接跳转、启动参数 |
   | 切换 | 点击、`Ctrl+Tab` / `Ctrl+Shift+Tab`、`Ctrl+1..9` |
   | 关闭 | 点击关闭按钮、`Ctrl+W`、中键点击 |
   | 关闭其他 / 关闭右侧 / 关闭全部 | 标签右键菜单 |
   | 重排 | 拖拽标签调整顺序 |
   | 恢复最近关闭 | 右键菜单或快捷键 |
   | 溢出访问 | 标签栏尾部下拉列表，列出全部已打开文档 |

4. **重复打开语义**：同一文件被再次打开时，激活已有标签，不新建重复标签；路径判定需兼容大小写差异、相对/绝对路径、符号链接解析后的同一文件。
5. **切换必须轻量**：
   - 切换标签不得重新解析未变化的文档。
   - 后台标签不得持续占用高成本渲染资源。
   - 切换回来后必须在可感知的短时间内显示内容，并恢复该标签的滚动位置。
6. **关闭语义**：
   - 关闭活动标签后，焦点与视图转移到相邻标签（优先右侧，其次左侧）；全部关闭后回到空状态界面。
   - 关闭标签必须释放该文档的监听器与重型资源（参见 NFR-002 / NFR-003）。
   - 首版无编辑功能，因此关闭标签不需要“保存确认”；未来引入编辑后必须补齐未保存提示。
7. **持久化**：标签集合、顺序、活动标签、每个标签的滚动位置需跨会话恢复；恢复时文件已不存在的标签静默跳过并进入“最近文件”列表。
8. **与其他功能的一致性**：
   - 目录、搜索、状态栏、主题均作用于**当前活动标签**。
   - 每个标签独立保存自己的滚动位置与搜索上下文。
   - App Theme 与 Markdown Theme 为全局设置，不随标签变化（每个标签不单独保存主题）。
9. **可访问性**：标签栏须为可键盘操作的可聚焦控件；活动标签需对辅助技术暴露“已选中”状态；关闭按钮需有可读的名称。

### 3.6 目录浏览与阅读工作台细则（FR-021）

**目标：** 采用 VS Code 式活动栏与阅读区布局，让现有目录中的文档可连续浏览；正文保持渲染阅读，不引入编辑或目录写入。

1. **同级入口**：最左活动栏提供文件 / 搜索 / 大纲三个入口；侧栏一次显示一个面板，再次点击当前入口收起。大纲不得嵌到文件树底部；搜索针对当前文档正文，不暗示已经支持全目录搜索。
2. **可伸缩侧栏**：侧栏可收起、可调宽，阅读区随之伸缩；切换面板保留当前会话的目录展开状态，文档大纲随活动标签更新。
3. **真实目录浏览**：通过文件夹选择器打开现有根目录，首次只列举根目录一层，展开子目录时才读取其子项；目录与 Markdown 可操作，其他文件置灰。显示根目录名称与当前文档，长路径可查看完整提示。
4. **标签联动**：点击 Markdown 新建标签或激活已有标签；缓存文档切换不重新解析，各自保留会话内阅读位置。更换根目录不关闭已打开标签；直接打开文件无需先选根目录。
5. **只读与权限**：不创建、重命名、移动或删除目录内容；宿主按已授权根目录校验每次枚举，拒绝路径越界与符号链接 / junction。目录枚举不扩大全局 asset scope，本地图片继续逐文件授权。
6. **异步与错误反馈**：显示加载、空目录、不可访问 / 消失、过多条目截断与重试；切换根目录后旧枚举结果不能覆盖新根目录。文件读取失败应保留其他标签并可继续阅读。
7. **验收与依赖**：对应 UC-10、AC-20..22 与 T24d，依赖宿主路径约束和 T24c 会话；遵守双主题、键盘导航、安全与非破坏性要求。真实 watcher、完整标签持久化、LRU 仍分别验收，不把基础工作台视为这些能力已完成。

| ID | 级别 | 分类 | 要求 |
|---|---|---|---|
| NFR-001 | P0 | 大文件性能 | 长文档和复杂文档打开、解析、滚动时应保持 UI 响应；避免在主线程执行长耗时解析任务 |

| NFR-007 | P0 | 离线可用 | 基础解析和渲染能力应由本地应用提供，不依赖在线渲染服务 |
| NFR-008 | P0 | 非破坏性 | 阅读及实时刷新不会改写原 Markdown 文件；用户阅读偏好独立保存 |

### 4.1 性能测试矩阵（测试场景，不是承诺的支持上限）

| 场景 | 样本 | 主要观察指标 |
|---|---|---|
| 小文件 | 100 KB 普通 Markdown | 冷启动、双击到首屏、交互流畅度 |
| 中等文件 | 1 MB Markdown | 解析耗时、目录生成、滚动表现 |
| 大文件 | 10 MB Markdown | 首屏时间、内存峰值、UI 响应 |
| 极大文件 | 50 MB Markdown | 退化行为、内存增长、失败恢复 |
| 图表密集 | 100 个 Mermaid 图表 | 按需渲染、任务队列、CPU 峰值 |
| 多文档 | 同时打开 10 / 30 / 100 文件 | 后台资源、标签切换、缓存策略 |
| 标签切换 | 20 份已打开的文档反复切换 | 切换延迟、是否触发重复解析、滚动位置恢复准确性（NFR-013） |
| 链接跳转 | 单文档内 200 个链接，逐个触发跳转 | 是否发生顶层导航、是否创建重复标签、错误链接的反馈延迟 |
| 长期使用 | 反复打开、关闭、修改文件 | 监听器与缓存释放、内存泄漏 |
| 更新压力 | 外部编辑器短时间连续保存 | 去抖、版本一致性、无重复高耗时渲染 |

**性能基准原则：** M0 阶段先指定测试环境，实测记录冷启动、首屏、P95 交互延迟、CPU、峰值/稳定内存；再制定具有可复现性和硬件前提的量化验收阈值。暂不凭空承诺“50 MB 必须在 X 毫秒内渲染”或“100 标签必须常驻”。

**公平比较原则：** 同一硬件、同一测试文件、相同字体与窗口大小、相同的功能完成度、相同测量口径。**内存必须统计进程树（含 WebView/Chromium 子进程），不能只看宿主 EXE。** 同时单独记录冷启动与热启动、首次完整渲染与首屏可读时间。对于原生原型暂不支持的扩展，必须明确标记“缺失”，不能以关闭 Mermaid/公式换取不公平的性能优势。

## 5. 技术方案与架构选型（主线暂定；M0 后冻结）

### 5.0 主开发技术栈 — 暂定选择（2026-10-28）

**默认主线：Tauri 2 + Vue 3 + TypeScript + markdown-it + HTML/CSS/SVG。** 这是一项可立即用于工程初始化的选择，不是“已经实测为最优”的结论。项目先把预览功能做对、做完整，再对真实资源开销进行验证。

| 层次 | 默认选择 | 使用边界或注意事项 |
|---|---|---|
| Desktop Host | **Tauri 2** | Rust 宿主、系统文件关联与原生能力；运行时依赖按平台解决 |
| UI | **Vue 3 + TypeScript + Vite** | 处理窗口内 UI、标签、目录、设置、App Theme；不将所有 Markdown 节点做成 Vue 组件 |
| 包管理 | **pnpm** | 锁定依赖版本，方便离线构建与可复现发布 |
| Markdown Parser | **markdown-it** | 单一主解析器；Token 流 / 渲染规则 / 插件作为内部扩展机制；不同时并用 unified 解析同一文档 |
| GFM 与补充语法 | markdown-it 内置规则 + 精选插件/自有小规则 | 核对 GitHub 兼容情况；任务列表、脚注、Alerts 等必须额外验证，不能误认为全部原生包含 |
| 正文渲染 | **HTML + CSS + SVG（系统 WebView）** | 文档 UI 与应用 UI 隔离，安全地加载本地资源；优先防止大 DOM 导致卡顿 |
| Mermaid | **Mermaid.js**（本地打包） | 图表延迟生成 SVG、错误局部隔离、缓存和重绘控制；默认严格安全配置 |
| 公式 | **KaTeX** | 行内/块级公式，适配 Markdown Theme |
| 代码高亮 | **Shiki** | 高亮器复用、按需加载语法和主题；大代码块异步处理 |
| App Theme | CSS Variables / Vue UI tokens | 仅控制程序外观 |
| Markdown Theme | 独立 CSS 作用域 + 代码/图表主题映射 | 仅控制文档渲染内容，不重解析普通文档即可切换 CSS |
| 原生文件核心 | Rust / Tauri Commands | 打开、文件路径校验、资源解析、文件变更通知、未来保存接口 |
| 外部变更 | Tauri FS watch 或 Rust notify | 父目录监听、去抖、原子替换兼容、版本检查、旧任务结果丢弃 |
| 文档调度 | Web Worker + Render Scheduler | 后台解析、标签优先级、缓存预算；Mermaid 如需 DOM 则由受控主线程渲染阶段完成 |
| 多文档状态 | Pinia + Document Manager | 仅活跃文档保留重型视图，后台文档保存轻量状态或按预算缓存 |
| 测试与基准 | Vitest + Playwright + Rust tests + fixture/benchmark 脚本 | 针对语法正确性、文件刷新和性能分别测试；统计 WebView 子进程资源 |

**选型理由：** 阅读预览兼容性优先，官方 Mermaid、KaTeX、Shiki 和 CSS 主题集成成本较低；Tauri 保留跨平台能力而不在发布包内携带完整 Chromium。**不能由此推断** Tauri 的运行时内存一定低于 Electron，也不能推断 Web Renderer 一定优于 Qt 原生排版。

**原生对照：** Qt 6 + QTextDocument/MD4C（不嵌入 WebView 做正文）只用于 M0 的最小比较实验。要明确标注未实现的 Mermaid/HTML/公式等功能，公平记录“性能收益”和“功能缺口/适配成本”，不开发第二套正式产品。

**架构转换条件：** M0 如果证明主线存在无法接受的严重兼容性问题、资源不可控问题或特定目标平台的运行依赖障碍，应记录量化证据，重新评估 Qt 原生或自带 Chromium（如 Electron/Qt WebEngine）；不能只因某一项微基准更快就全盘改写架构。

**工程实施约束：** Markdown Engine、文档状态及文件操作通过少量稳定接口组织；不要提前设计通用多后端渲染插件平台，不要要求源码在 Tauri/Qt 之间完全无改动迁移。

### 5.1 渲染路线选择的依据

Markdown 渲染至少包含 **语法解析（Parser）→ 文档结构（AST/事件）→ 布局与绘制（Renderer）** 三部分。Parser 不是 WebView；HTML 只是可选的中间格式。不能把 Tauri/Wails/Electron/WPF + WebView2 当成四种不同的“Markdown 渲染路线”比较。

| 方案 | 核心路线 | 主要优势 | 主要风险／成本 |
|---|---|---|---|
| A — Web 排版 | Markdown → AST/HTML → CSS/DOM/SVG → WebView/Chromium/WebKit | CSS Theme、HTML、Mermaid、公式生态成熟；兼容性与实现速度较好 | 浏览器基线开销；长文档 DOM、SVG、后台标签的内存和响应需要优化；系统 WebView 依赖需管理 |
| B — 原生文档排版 | Markdown → AST/事件 → Qt QTextDocument、WPF FlowDocument、原生 Text/Layout | 无须浏览器绘制正文；可专项优化文本模型、布局与资源回收 | 对完整 HTML/CSS、复杂表格、Mermaid、公式和跨平台 Theme 的支持成本更高 |
| C — 混合式 | Markdown → 原生正文；Mermaid 等独立生成 SVG/图像 → 原生嵌入 | 有机会兼顾原生正文与丰富图表；普通文档不一定需要 WebView 排版 | 两种引擎的协调、字体度量/布局一致性；若辅助引擎需浏览器，仍会产生浏览器运行成本 |

**当前结论：** A 已选为**默认开发主线**，B 作为 M0 的受限对照实验，C 为未来基于证据重新评估的备选。**M0 可以有两个最小原型，但 M1 只开发一套正式渲染器。**

### 5.2 其他技术候选（用于验证或替换，不是当前主线）

| 技术层 | Web 路线候选 | 原生路线候选 | 选择标准 |
|---|---|---|---|
| Markdown Parser | unified/remark/rehype、markdown-it；可评估 cmark-gfm/Comrak 输出 HTML | Qt Markdown/MD4C、Comrak、Markdig | CommonMark/GFM 兼容性、扩展能力、速度、峰值内存、节点/源码位置能力 |
| 文档布局与绘制 | DOM/CSS/SVG，系统 WebView 或自带 Chromium | Qt QTextDocument / 自定义原生富文本 | 视觉正确性、复杂排版与长文档响应、可选择/搜索、资源占用 |
| Mermaid | 官方 Mermaid JS（本地打包） | 原生阅读器嵌入已生成 SVG；图表生成引擎需单独验证 | 是否支持目标图表类型、主题切换与跨平台字体度量；不默认为原生支持 |
| 公式 | KaTeX（Web） | 原生公式排版、离线 SVG/图像生成等候选 | 公式兼容性、字号与文本基线、性能 |
| 代码高亮 | Shiki | Qt/QSyntaxHighlighter 或其他 lexer/主题映射 | 语言覆盖、主题支持、长代码性能 |
| UI 框架 | Vue 3 + TypeScript（如果采用 Web UI） | Qt Widgets / Quick；Windows 特定候选 WPF | 对 Reader UI 与 App Theme 的适配成本 |
| 桌面宿主 | Tauri 2、Wails、Electron、Qt WebEngine；宿主在选定 Web 路线后进一步比较 | Qt 桌面应用；Windows 特定候选 .NET/WPF | 系统文件关联、安装依赖、跨平台能力、总进程资源与开发维护成本 |

> **重要：** Tauri 已是**暂定开发主线**，但不是“实测后永久冻结”的架构。如果使用 Tauri，Windows 使用 WebView2，macOS 使用 WKWebView，Linux 依赖 WebKitGTK；如果采用 Electron/Qt WebEngine 等自带引擎方案，仍有浏览器运行开销，但可减少对系统预装 WebView 的依赖。不同系统的字体、CSS/SVG 与 Mermaid 结果仍需实测。

### 5.3 与宿主、渲染器解耦的逻辑架构

```text
Desktop Host / Native Shell（Tauri 2 暂定）
    ├── 文件关联 / 进程启动 / 窗口 / 安装依赖 / 系统命令
    ├── Document Manager
    │      ├── File Reader + Path/Resource Resolver
    │      ├── File Watcher + Live Reload Coordinator
    │      └── 多文档状态与生命周期
    ├── Render Scheduler
    │      ├── 优先级 / 去抖 / 取消 / 版本校验
    │      └── 缓存预算 / 后台标签 / 资源回收
    ├── Markdown Parser + Extension Pipeline
    │      ├── CommonMark / GFM / Alerts / Math
    │      └── Document Model（AST 或语义事件）
    ├── Renderer Adapter（M0 选型）
    │      ├── Web DOM/CSS/SVG       [候选 A]
    │      └── Native RichText/SVG   [候选 B/C]
    ├── Reader UI（预览、导航、搜索、图表操作）
    └── Theme System
           ├── App Theme
           └── Markdown Theme（包括图表/公式/代码主题映射）
```

以上是**逻辑职责**，不是要求独立进程、复杂插件框架或同时支持多渲染后端。M0 通过后，正式代码只需要实现一种主渲染器；为后续调整保留少量清晰接口即可。

### 5.4 大文件、多文件性能设计原则

- **耗时任务避让 UI：** Web 路线可用 Web Worker；原生路线使用后台线程/任务队列；不允许主线程长时间同步解析整个大文件。
- **渐进显示与可见优先：** 优先展示正在阅读的内容；图表、代码高亮等昂贵操作按需调度。
- **结构感知分段：** 不按固定字符数硬切 Markdown；首先完整解析后按块管理显示，再根据基准决定是否需要增量解析/虚拟化。
- **多标签资源预算：** 非活动文档可仅保留路径、元数据、阅读位置与失效标记；完整 DOM、AST、SVG、图片缓存有上限、可释放。
- **任务代次与中止：** 外部修改、切换/关闭标签时，旧任务即使无法物理取消，也不得提交过时结果；关闭后应释放观察器、定时器和资源句柄。
- **主题切换：** App Theme 与 Markdown Theme 独立。Web CSS 主题尽量直接更新样式；Mermaid 等按需重绘，避免重新解析 Markdown。
- **持续观测：** 记录冷/热启动、首屏、完整渲染、P95 交互、总进程树 RSS/工作集、CPU 空闲、反复打开关闭后的泄漏趋势。

### 5.5 实时更新技术原则

采用 **文件系统通知 + 去抖/合并 + 内容/版本校验 + 优先级渲染**；正确处理直接覆写与编辑器“临时文件写入 → 原子替换”的保存方式。需要时监听父目录并按路径重新关联。仅当读到完整且有效的文件版本后更新视图，读取失败保留旧版本并提示。后台标签可延迟昂贵渲染，但切回时应显示最新有效内容。

M0 应验证刷新时能保持滚动/章节位置、不会旧结果覆盖新结果，并确认“读取与显示最新保存版本”与“编辑器未保存缓冲区实时同步”是不同需求，**首版只承诺前者**。

### 5.6 安全、离线与样式隔离

- 非信任 Markdown 中的 HTML、链接、SVG、远程图片及自定义 CSS 需要明确的安全策略；禁止 Markdown 任意执行脚本。Mermaid 使用安全默认配置，出错可展示源码/错误占位。
- 本地资源访问限制在文档及其必要引用范围；不得为了方便直接放开整盘读取权限。
- 常见 Markdown 渲染与 Mermaid、公式依赖本地打包；基本阅读离线可用。
- App Theme 与 Markdown Theme 逻辑独立；Web 路线可比较 Shadow DOM/明确 CSS 命名空间，原生路线需分别管理控件主题与文档样式。

### 5.7 缺少 WebView/运行库的处理（正式发布阶段实施）

| 情况 | 需要做到 | 实施节点 |
|---|---|---|
| Windows 缺少或损坏 WebView2 Runtime | 安装包检测或框架原生引导，给出组件名、官方安装/修复方式 | Windows 安装包发布前 |
| Linux 缺少 WebKitGTK、图形或字体等依赖 | 按发行包形式列明必要依赖、安装指引及不支持的环境 | Linux 版本发布前 |
| macOS 系统版本过旧或 WebKit 不满足要求 | 明确最低系统版本，并给出升级或兼容性说明 | macOS 版本发布前 |
| 采用自带 Chromium/Qt WebEngine | 列出最低图形、系统库与 GPU/软件渲染条件；不能声称“零依赖” | 对应版本发布前 |
| 环境不可修复 | 显示通俗的错误与诊断信息；说明不可用原因和处理路径 | 对应版本发布前 |

**设计约束：** 如果缺失 WebView 会导致主窗口无法创建，提示不能只放在依赖 WebView 的 Vue 页面中；应借助安装器、宿主原生启动检查或独立引导界面。现在记录要求并在技术原型中摸清依赖，**具体检测、交互与修复流程在选定宿主和发布平台后实现**。不因少数环境缺少 WebView 就提前维护第二套正式渲染器。

## 6. 依赖关系与模块影响

| 模块/能力 | 必要依赖 | 可能影响/被影响 |
|---|---|---|
| Reader View | Markdown Parser、Renderer Adapter、Document Manager | Markdown Theme、目录导航、搜索、图表查看 |
| Live Reload | Document Manager、文件监听、Render Scheduler | 缓存失效、阅读位置、后台标签、未来编辑冲突 |
| Markdown Theme | 所选 Renderer 的稳定样式接口、主题系统 | Mermaid、代码高亮、公式样式适配 |
| Mermaid 渲染 | 解析扩展、图表生成器、Renderer 嵌入接口 | 任务调度、性能缓存、安全策略、主题切换 |
| 大文件性能 | Document Manager、Engine、Scheduler、Reader View | 解析策略、DOM 数量、图表调度、缓存预算 |
| 简单编辑（未来） | Document Manager、文件版本与写入策略 | Live Reload 冲突、保存操作、编辑器组件 |

**主要实现顺序依赖：** **M0 按主线验证与技术决策（Qt 已跳过）** → 文件打开/文档状态 → 基础解析与阅读视图 → 扩展渲染 → 文件变更同步与多文件管理 → 完整主题适配和阅读增强。2026-11-04 按用户决定先推进目录与多标签 UX 切片；性能专项后置，原性能目标与未达标记录继续有效，安全约束随功能验证。

平台运行库检测/修复属于**发布门槛**，M0 仅记录并实验依赖条件；不能让这个后期事项阻断当前验证。

## 7. 里程碑与验收

### M0 — 渲染架构验证与技术冻结（**现在启动**）

> 本节保留原 M0 计划供追溯；2026-11-04 用户已确认跳过 Qt 对照，不安装或补测 Qt。当前仅 Web 主线有实测，原性能未通过项见 [测试结论](../../benchmarks/findings.md)，不因 UX 迭代改写。

**目标：** 先按已暂定的 Web 主线完成可复现的 Markdown 渲染实验，再通过 Qt 原生对照确认核心取舍；验证后冻结正式技术选型。不是一开始写完整桌面 UI。

- 建立 Markdown 测试夹具：基本语法、GFM、Alerts、公式、Mermaid、多种 HTML/相对资源、100 KB/1 MB/10 MB/50 MB、100 图表、10/30/100 文件。
- 完成原型 A（**主线** Web Renderer）：在独立浏览器/WebView 测试容器中渲染同一测试集，验证 Mermaid、KaTeX、Shiki、CSS Theme、文件更新和安全策略。
- 完成原型 B（**受限对照** Native Renderer）：以 Qt QTextDocument/MD4C 等为起点渲染同一测试集，记录原生布局、图文混排、主题和扩展缺口，实验 Mermaid SVG 嵌入的可行性。
- 同环境测量渲染正确性、冷/热启动、首屏可读、交互、内存/CPU、重复打开关闭与实时更新；记录缺失功能，不用简化功能换取虚假的性能对比。
- 评估运行依赖与发布可行性（系统 WebView、图形库、所需系统版本）；**只研究并记录，发布修复流程后续实施**。
- 编写技术决策记录（ADR）：选定一个正式 Renderer、Parser、UI/Host 组合，并说明未选方案为何不适合目前需求。

**M0 完成定义：** Web 主线原型与 Qt 最小对照、统一测试文件、性能记录、兼容性差异表、选型 ADR 和 M1 工程初始化计划俱全；无须把原型 B 的所有复杂扩展都做完，但必须准确说明实现成本与差距。

### M1 — 首个可日常使用的预览器

**目标：** 作为 `.md` 默认打开方式日常使用。

- 在 M0 所选主渲染架构上建立正式桌面工程。
- 完成全部 P0 功能：基础与常用扩展渲染、文件关联、多文件、双主题、基础导航、Live Reload、完整多标签与目录浏览工作台（FR-021）。
- 异常文件不会导致应用崩溃；文件更新后显示最终有效版本。
- 核心性能与资源管理机制可运行，性能阈值按 M0 测试结果验收。

**通过条件：** 不进入编辑模式也能完成“打开—阅读—外部修改—自动刷新—继续阅读”的完整闭环，并通过目录浏览 / 同级活动栏验收。本轮基础 UX 不等于完整 M1 通过。

### M2 — 阅读体验完善

图表/图片增强操作、阅读位置恢复、丰富的 Markdown 主题、更多个性化阅读配置与兼容性优化；针对首发平台完善安装器和运行依赖错误提示。

### M3 — 便利能力（按需）

外部编辑器联动、简单编辑、导出/转换等。优先选择能减少软件切换、又不损害预览主线的能力。

## 8. 明确不做与暂不承诺

- **不以专业 Markdown 编辑器为目标**，不追求完整 IDE、智能补全或协同编辑能力。
- 不强制管理文档库、工作区、知识库或账户系统。
- 可选只读文件树属于阅读导航；不要求创建项目、写入目录配置或引入完整 IDE。
- 首版不需要后端服务器、在线同步服务或插件市场。
- 不预先承诺所有 Markdown 方言 100% 兼容；按照语法测试样本持续补全。
- 不在缺乏基准前承诺极端大文件、多标签数量的固定响应时间和内存上限。
- 不为了功能数量而实现复杂导出、批处理或编辑功能。
- 不在首版同时实现 Web 和原生两套正式渲染引擎；M0 的第二原型是用来决策、并非长期维护承诺。
- 不把“支持 Linux/macOS”误认为“没有系统依赖”；正式支持的平台必须列出可理解的安装要求和修复方式。

**Git 后续规划：** 在阅读工作台后续考虑仓库状态、变更列表与差异查看；提交、同步和远端操作范围待定，不属于本轮实现与授权。本轮没有已实现的 Git 功能，也不增加无效入口。
